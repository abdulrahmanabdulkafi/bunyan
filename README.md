# بُنيان — منصة البنية المؤسسية للجهات الحكومية

النواة العاملة (MVP) من الإصدار الأول وفق وثيقة متطلبات العمل (BRD): مستودع بنية مؤسسية متعدد الجهات، مبني على **النموذج العام لمحتوى البنية المؤسسية** الصادر عن هيئة الحكومة الرقمية، ويركز على مجالات **التطبيقات والتقنية والأمن السيبراني**.

### إضافة موصّل جديد

كل موصّل كائن واحد في `apps/api/src/integrations/connectors.ts` يعرّف: الإعدادات (وما هو سري منها)، وأنواع العناصر التي يقرؤها وحقولها، والربط الافتراضي، ودالتي `test` و`fetch`. ما عدا ذلك (التشفير، المطابقة، الدمج، المسودات، الجدولة، سجل التشغيل) يتولاه الإطار. الطلبات الصادرة تمر عبر `requestJson` الذي يمنع عناوين البيانات الوصفية السحابية والعناوين المحلية.

### إضافة منظور جديد

كل منظور سطر في `apps/api/src/viewpoints/catalog.ts` بأحد خمسة أنواع: `list` و`matrix` (مع `via` للعلاقات غير المباشرة) و`group` و`nest` و`graph` (مع `collapse` لاختصار عنصر وسيط). المحرك يبنيه من المستودع، والواجهة تعرضه دون تعديل.

## البنية التقنية

```
apps/api     NestJS 12 + PostgreSQL (pg) — REST تحت /api
apps/web     Next.js 16 (App Router) — واجهة عربية RTL، تمرّر /api إلى الخادم
db/          ترحيلات SQL (الجداول، سياسات RLS، الصلاحيات)
packages/seed/metamodel.seed.json   النموذج الوطني المستخرج من وثيقة الهيئة
scripts/db-setup.mjs                إنشاء الأدوار وقاعدة البيانات والترحيلات والبيانات التجريبية
```

**العزل بين الجهات**: التطبيق يتصل بدور `bunyan_app` الذي لا يملك الجداول ولا يتجاوز RLS. كل طلب يعمل داخل معاملة تضبط `app.tenant_id`، فلا تعيد قاعدة البيانات سوى صفوف الجهة حتى لو أخطأ الكود. الدالتان الوحيدتان اللتان تقرآن عبر الجهات (البحث عند الدخول، والمؤشرات المجمّعة) يملكهما دور منفصل `bunyan_definer`.

**النموذج قابل للتهيئة**: كل جهة تحصل عند إنشائها على نسخة من النموذج الوطني، وقيم السمات تُخزَّن في JSONB وتُتحقَّق مقابل تعريف الوحدة عند كل حفظ أو استيراد.

## التشغيل محلياً

المتطلبات: Node 22 وPostgreSQL 16.

```bash
npm install
ADMIN_DATABASE_URL=postgres://postgres@localhost:5432/postgres npm run db:demo   # يعيد إنشاء قاعدة البيانات مع بيانات تجريبية
npm run build
npm --workspace apps/api start      # http://localhost:4000/api
npm --workspace apps/web start      # http://localhost:3000
npm test                            # 45 اختبار تكامل على قاعدة بيانات حقيقية، منها خادم vCenter وخادم LDAP وهميان
```

أو عبر Docker: انسخ `.env.example` إلى `.env` وغيّر القيم، ثم `docker compose up --build` (أضف `--profile sso` لتشغيل Keycloak).

## ملاحظات للمطورين

- **القوائم المعرّفة مسبقاً**: وثيقة الهيئة تحدد نوع السمة "قائمة معرّفة مسبقاً" دون قيمها في أغلب الوحدات، فتعمل كنص حر حتى يعرّف مسؤول البنية القيم من «تهيئة النموذج».
- **الفصل بين المهام**: من عدّل السجل آخر مرة لا يستطيع اعتماده. الجهة التي لديها مسؤول بنية واحد تحتاج مهندساً أو مالك بيانات للاعتماد المبدئي.
- **تعديل سجل معتمد** يعيده مسودة ليُعتمد من جديد؛ النسخة السابقة محفوظة في سجل التدقيق.
- **الإنتاج**: `JWT_SECRET` و`CONNECTOR_KEY` (32 بايت بترميز base64، لتشفير اعتمادات الموصّلات) إلزاميان عند `NODE_ENV=production`. الجلسة تُحفظ في sessionStorage وتنتهي بعد 8 ساعات.
- **المزامنة المجدولة** تعمل داخل خادم الواجهة البرمجية كل دقيقة، ويمنع قفل في قاعدة البيانات تشغيل الموصّل نفسه مرتين عند تعدد النسخ. عطّلها بـ `SCHEDULER=off`.
- **ما يرد من الموصّلات** يدخل مسودة، وأي تغيير على سجل معتمد يعيده مسودة، إلا إذا فُعّل «الاعتماد التلقائي» للموصّل.
- **اللغة**: نصوص الواجهة في `apps/web/lib/messages.ts` (العربية أولاً ثم الإنجليزية)، ورسائل الخادم في `apps/api/src/common/i18n.ts`.
